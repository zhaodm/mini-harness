## 问题清单

### CP-2: PM 越权修改技术产物

- **现象:** PM 收到用户 4 点 SA 设计补充意见后，直接编辑 sa/design.md 写入技术内容，而非调度 SA 完善
- **根因:** CLAUDE.md §2 角色隔离是自然语言软约束，PM 在"效率优先"压力下自动忽略。CR-001-E 已尝试修复（pm.md 加一句话），证明无效
- **影响:** 技术决策质量无保障，角色隔离形同虚设

### CP-3: PM 越权修复代码

- **现象:** Batch-1 完成后 PM 执行 typecheck 发现 6 个类型错误，PM 直接修改 6 个源码文件修复，未派发 DE
- **根因:** 框架对"门禁 FAIL 后怎么办"无定义，PM 被迫直接改代码。缺失环节：门禁失败 → PM 归因 → 创建修复 handoff → DE 修复 → PM 复验
- **影响:** PM 承担 DE 职责，修复质量无审计覆盖

### CP-4: 单任务 Token 消耗过高

- **现象:** T1（DI 容器重构）消耗 90,875 tokens / 111 tool uses / 30 分钟
- **根因:**
  - 任务粒度过大（240 行重构 + 3 新文件 + 集成测试 = 单 Agent 认知负担重）
  - SubAgent 环境无法执行 pnpm typecheck，Agent 反复尝试导致无效 tool calls
  - Agent 反复读取相同文件确认上下文
- **影响:** Token 浪费，执行时间拉长

### CP-5: DE 直接写入根目录 output/

- **现象:** 所有 DE SubAgent 将代码直接写入项目根目录 `output/`（最终归档目标），而非按框架设计写入 `deliverables/REQ002/output/`（开发暂存区）
- **根因:** PM 在 handoff 白名单中直接写了 `output/packages/server/src/...` 作为输出路径。框架对 CHANGE 模式（修改已有代码）的路径语义无明确规定
- **影响:** 无法做归档前完整性校验、无法做 diff 对比、SR4 驳回时无法干净回退

### CP-6: 归档文件位置不遵循目录结构

- **现象:** 归档文件位置和命名不遵循已有 output/docs/ 目录结构，不同需求的文档混在同一目录
- **根因:** mh-archive.md 硬编码了 `output/spec/` 路径，与实际项目结构冲突。归档前没有"先读再写"的强制步骤
- **影响:** SR4 被驳回 1 次

### CP-7: SR4 审批混淆

- **现象:** PM 在 apply 阶段用户说"通过"后，将其误认为是 archive 阶段的 SR4 结项确认，直接将 state 标记为 done
- **根因:** apply "通过" = 代码审批（SR3），archive "确认结项" = 归档完整性（SR4），两者措辞相近，框架中两个节点的触发条件区分不够
- **影响:** 流程状态跳跃，跳过归档步骤

### CP-8: 产出文档无 REQ-ID 隔离

- **现象:** 归档时 PM 将文档直接放在 output/docs/ 下，不同需求文档混杂
- **根因:** 框架无强制机制确保文档产出落在 {req-id}/ 子目录下
- **影响:** SR4 被驳回 1 次

## 经验总结

### EXP-1: 自然语言约束对 AI Agent 无效

- 来源: CP-2, CP-3
- CR-001 用自然语言修复越权问题，REQ002 中完全无效
- 结论：能用脚本阻止的，不靠文字描述
### EXP-2: "设计了但没接线"= 没设计

- 来源: CP-5 (.archiveignore 存在但未执行)
- .archiveignore 已正确生成 40+ 条规则，但归档时 PM 完全没读取
- 结论：机制的存在 ≠ 机制的执行，必须验证端到端接通

### EXP-3: 质量门禁失败需要结构化归因流程

- 来源: CP-3
- 门禁 FAIL 后框架无定义，PM 被迫直接改代码
- 结论：需要模板引导 PM 归因而非动手修

### EXP-4: Handoff 需标注环境限制

- 来源: CP-4
- Agent 不知道哪些命令不可用，反复尝试浪费 token
- 结论：handoff 应包含环境限制、预读文件清单、Token 预算参考

### EXP-5: CHANGE 模式需明确读写路径分离

- 来源: CP-5
- 修改已有代码时，"读源码"路径和"写产出"路径必须分离
- 结论：DE 的写路径只能是 deliverables/{REQ-ID}/output/

### EXP-6: output_type=custom 需强制追问验证策略

- 来源: REQ002 执行观察
- custom 类型如果 clarify 阶段不明确验证方式，后续 DE/TE 无法自验
- 结论：verify.sh 应检查 custom 类型的 test_strategy 不为空

### EXP-7: 归档路径不能硬编码

- 来源: CP-6, CP-8
- mh-archive.md 假设 `output/spec/` 结构，与实际项目冲突
- 结论：归档前必须先探测已有结构再写入

## 改进方向概览

本复盘识别出 11 个系统性问题域，核心改进方向：

1. **Hook 层实时阻止越权**（替代自然语言禁令）
2. **质量门禁失败归因流程**（替代 PM 直接修复）
3. **.archiveignore 端到端接通**（脚本层真正执行）
4. **Handoff 结构化环境信息**（减少 Agent 盲目探索）
5. **归档路径自适应**（脚本校验替代硬编码假设）

具体方案见：`docs/requirements/CR-003-framework-improvements.md`
